\section{Problem and requirements}
Online customers search for products in different ways: they may type a description, speak a query, or provide a product image. The system converts each input to a common query format, retrieves candidate products, ranks them, and displays the results. Customers can also look up their own orders.

The prototype connects requirements analysis, UML design, a three-layer architecture, and executable Python code. It has a short console example and a local browser interface. The browser can recognize microphone speech and pass its transcript to Python; typed transcripts remain available. Image search uses Apple's Vision framework through a local Swift process on macOS.

\begin{center}
\fcolorbox{navy}{pale}{\parbox{0.88\linewidth}{\centering Text, voice, or image $\longrightarrow$ common query $\longrightarrow$ candidate retrieval $\longrightarrow$ ranking $\longrightarrow$ results}}
\end{center}

\textbf{Primary actor:} Customer. A customer ID is supplied for order lookup; the repository checks ownership before returning an order.

\subsection*{Service responsibilities and search logic}
\begin{table}[H]\small
\caption{UML classes and Python modules}
\begin{tabularx}{\linewidth}{@{}p{34mm}Y@{}}\toprule
Layer / component & Implementation \\ \midrule
Presentation & SearchUI collects mode-specific input and displays results. \\
Query handling & QueryService normalizes input into a common query. \\
Voice and image & SpeechService passes the transcript; ImageService validates the uploaded photo. \\
Product search & SearchService retrieves candidates; RankingService sorts them. \\
Order search & OrderService handles order ID and latest-order requests. \\
Data & Repositories load JSON; VectorIndex stores Vision feature prints for product photos. \\
\bottomrule\end{tabularx}
\end{table}

\textbf{Text and voice.} QueryService lowercases text, normalizes a small set of category synonyms, and detects common colors, brands, and price limits. SearchService applies the detected filters before ranking. In the browser, the Web Speech API turns microphone speech into editable text. SearchUI then sends that transcript through SpeechService and the same query path. The console example and saved voice checks use supplied transcripts, so they do not measure recognition accuracy.

\textbf{Image search.} ImageService validates the uploaded file. VectorIndex uses Apple's \href{https://developer.apple.com/documentation/vision/vngenerateimagefeatureprintrequest}{Vision feature-print API} to describe each catalog photo and the query photo. Vision measures their visual distance $d$; a smaller distance means a closer match. The application displays the equivalent similarity $S_i=1/(1+d)$, so a larger displayed score is better. The same Vision index is used by the running Python application and the evaluation script. It requires macOS and Swift.

\textbf{Ranking.} The business score $B$ combines popularity and in-stock status. Text or voice search uses $0.9S_t+0.1B$. Image-only search uses $S_i$, preserving Vision's visual order. When both text and image are supplied, the score is $0.45S_t+0.45S_i+0.1B$. Retrieval selects eligible candidates; RankingService sorts those candidates by score.

\textbf{External data.} The browser and evaluation use 500 real grocery products and 100 separate alternate-view query images from Open Food Facts. Gallery and query photos are kept as distinct files; a query photo is never used in the gallery index. Every product has a barcode and title; 350 have a brand and 204 have a usable broad category. Source selection, attribution, and license details are in \path{data/openfoodfacts/DATASET.md}.

\nextsection{Evaluation}
\textbf{What is measured.} Each test asks whether the application's first result is correct. For exact-product image search, the correct answer has the same barcode as the query photo. We also count whether it appears anywhere in the first five results.

\textbf{Source and test setup.} Product records come from the official Open Food Facts \href{https://static.openfoodfacts.org/exports/products.random-modulo-1000.tar.gz}{random-modulo-1000 sample}; photos come from its image store. A fixed selection provides 500 catalog products and 100 separate query photos. The catalog contains a product's front photo, while its different query photo is kept out of the index. Thus, matching requires recognizing the same product across two views. The selection seed, source hash, and image attribution are supplied with the dataset.

\textbf{Method.} The test calls the submitted Python application's SearchUI, SearchService, and Apple Vision index. The category check asks whether the first result has the same broad Open Food Facts category; 48 of the 100 queries lack a usable label and are excluded from that check. For text, the query is the catalog's own product title, which is easier than a customer's free-form request. Voice checks use known transcripts and assess retrieval after transcription; live microphone recognition is demonstrated but not scored.

\nextsection{Discussion and conclusion}
The prototype meets the required tasks: it defines the customer requirements, models all required use cases and the three layers in Visual Paradigm, illustrates voice search, and implements text, voice-transcript, image, and ranked results in Python. The browser adds live microphone transcription. It also demonstrates text-image fusion, price filtering, and order ownership checks.

The main limitation is exact-product image retrieval: the Apple Vision method finds the correct product first for 22 of 100 alternate-view photos. It also requires macOS and Swift. The teaching catalog is small; the real-photo sample is grocery-focused and much smaller than a real store. Text evaluation uses exact product titles. Microphone recognition depends on browser support, permission, and the browser's recognition service; its accuracy is not measured here. The supplied customer ID is not an authentication mechanism.

A practical next step is to test product-specific image representations or package-text recognition on the same held-out photos. The current service boundaries allow that change within the image index without moving search logic into the user interface.

\textbf{Reproducibility.} The GitHub submission contains the report, editable \code{.vpp} project, Python source, browser interface, teaching records, README, thirteen automated tests, and saved evaluation results. The prepared Open Food Facts photos and metadata are provided as a separate ZIP on Google Drive. The README provides a tested \code{gdown} command, checksum, and extraction steps. The UML project can be rebuilt with \path{tools/build_vp.py}; the report uses the supplied Assignment 06 handout as its specification.
